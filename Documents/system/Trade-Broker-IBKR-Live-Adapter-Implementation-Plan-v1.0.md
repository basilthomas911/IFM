## 1. Inputs, prerequisite and release boundary

This plan implements the live **framework** IBKR order/account ports and the corresponding **application** `ITradeBroker` concrete adapter from the [architecture design](Trade-Broker-Application-and-Framework-Architecture-Design-v1.0.md) and [BrokerOrder/Accounting specification](Trade-Broker-BrokerOrder-Execution-and-Accounting-Specification-v1.0.md). It follows [Actor Implementation Conventions](Actor-Implementation-Conventions.md), [compile-time structured logging](System-Wide-Telemetry-and-Distributed-Tracing-Design.md#811-compile-time-structured-logging-convention), and the framework [IBKR connection](../../TomasAI.IFM.Framework.TradeBroker.InteractiveBrokers/Docs/IbkrBrokerConnectionSpecification.md), [contract reference](../../TomasAI.IFM.Framework.TradeBroker.InteractiveBrokers/Docs/IbkrContractReferenceSpecification.md), [order adapter](<../../TomasAI.IFM.Framework.TradeBroker.InteractiveBrokers/Docs/IbkrOrderExecutionAdapterSpecification (1).md>), [broker account](../../TomasAI.IFM.Framework.TradeBroker.InteractiveBrokers/Docs/IbkrBrokerAccountSpecification.md), and [order workflow](../../TomasAI.IFM.Framework.TradeBroker.InteractiveBrokers/Docs/OrderExecutionWorkflowSpecification.md) specifications. The emulator and scripted test harness are separate; neither can become a silent fallback for a failed live/paper connection.

**L0 is a hard domain gate:** a named reviewer has accepted the Emulator manifest/approval ID produced by E11, and its code, MessagePack schemas, approved order shapes, profile, accounting and actor-contract versions remain applicable. The Live-adapter plan can be reviewed now, but **no live-adapter implementation begins before that acceptance**. If a material shared contract or business rule later changes, re-run affected Emulator qualification and obtain a new compatible acceptance before continuing. Paper or Live mode is never enabled merely by building the adapter.

The Live adapter does not create a new OrderExecution workflow, broker-domain lifecycle, financial book or learned execution policy. It maps the same approved BrokerOrder mutation events and account queries to real IBKR API calls, then maps exact callback evidence back through the same application observation bridge and actor messages. One configured allowlisted IBKR account is active per V1 host/session. This is a platform choice, not a claim that IBKR globally forbids multi-account sessions. The configured paper and live account aliases, credentials, client IDs and ports are separate; no synthetic/paper balance, fill, position or Fund posting is carried into Live.

## 2. Reused contracts and actor ownership

The [Emulator plan](Trade-Broker-IBKR-Emulator-Implementation-Plan-v1.0.md) must have delivered:

1. one Application `ITradeBroker` contract and versioned order/account/observation DTOs;
2. separate Framework `IFrameworkOrderExecutionBroker` and `IFrameworkBrokerAccount` ports;
3. `Trade/Order/Broker` BrokerOrder Command/Event/Query/Realtime actors and dedicated handlers;
4. BrokerAccount Command/Event/Query actors with qualification/hold/gate ownership;
5. revised TradeOrder/OrderExecution state and commands for actual broker ack/fill/cancel/unknown evidence;
6. generic micro-execution Models and Portfolio/Fund accounting handoff;
7. one hosted observation bridge, durable intent/correlation/inbox/approval storage and versioned Emulator acceptance evidence.

The live plan **reuses** all these types and their exact actor maps. It may append versioned provider-neutral fields only when a real IBKR gap is proven; it does not add `conId`, `orderId`, `permId`, `clientId` or raw TWS status strings to Domain trade identities. A string `ContractId` remains the order leg's exact broker-neutral contract identity; the framework adapter resolves IBKR `conId` internally. For application actors, broker `AcceptedForDispatch` remains a local receipt and an `execId`-keyed individual execution remains actual fill truth. Account cash and buying-power evidence belongs to BrokerAccount; Portfolio/Fund is still the internal financial book.

### 2.1 Actor convention audit before provider wiring

At L0 rerun Command/Event/Query/Realtime actor map parity and single-handler-file audits on `Trade/Order/Broker`, BrokerAccount and changed OrderExecution actors. For every mapped Command, `_parseMap` uses exact `Verb`, `_validationMap` uses exact concrete `Type` and returns all deterministic `ValidationError`s, and `_receiveMap` uses that same concrete `Type` to call its dedicated `Command/<MessageWithoutCommand>.cs` extension. `OnValidateAsync` delegates to `ValidateMappedCommand`, which raises one aggregate `CommandValidationException` **before state loading**. The map validator checks CommandId, intrinsic EntityId, serialized payload properties and cross-identity consistency; list extensions handle scalars/enums, FluentValidation handles structured reference payloads, and null payloads produce errors rather than exceptions. Actual account permission, session epoch, working-order revision, current gate and broker exposure are state/external checks in the dedicated handler **after** state loading, never a validation-map network call.

For every Event/Realtime mapped message, the actor uses exact `_parseMap`/`_receiveMap` with base parse/resolve helpers and a one-message extension file directly in its role folder. Every real handler failure is source-generated Error logged with OperationId/account alias/epoch and then returned/preserved through the base actor behavior; routine foreign/duplicate/no-op observations are classified without exception. Query actors retain exact `_parseMap`, `_receiveMap` and `_exceptionMap` parity with typed responses. No live-adapter provider callback may bypass BrokerOrder EventActor and write OrderExecution state directly. No new FunctionActor is required for broker I/O: price and constraint decisions stay in pure `Broker/Model`, and all durable mutations start as Command/committed Event.

Dedicated BrokerOrder handlers from Plan 1 remain in force: `InitializeBrokerOrder`, `RequestPlaceBrokerOrder`, `RequestUpdateBrokerOrder`, `RequestCancelBrokerOrder`, `RecordBrokerDispatchReceipt`, `RecordBrokerOrderAcknowledgement`, `RecordBrokerExecutionObservation`, `RecordBrokerCommissionObservation`, `RecordBrokerOrderFailure`, `RecordBrokerReconciliation`, `EvaluateMicroExecution`; Event handlers `OrderExecutionChanged`, `BrokerOrderPlaceRequested`, `BrokerOrderUpdateRequested`, `BrokerOrderCancelRequested`, `BrokerOrderAcknowledged`, `BrokerExecutionReported`, `BrokerCommissionReported`, `BrokerOrderFailureReported`, `BrokerOrderReconciled`, `BrokerAccountGateChanged`; Query and Realtime handlers remain equally one-per-message. If a newly supported IBKR callback needs a new domain message, append one contract, one parse entry, one receive entry, one dedicated extension class/file, one validation entry for a Command, source-generated logs and focused happy/edge tests in the **same gate**.

### 2.2 Guard and state-update invariants

Before Live provider dispatch, `RequestPlaceBrokerOrder` checks an exact paper qualification/Paper accepted/Live pilot approval scope, correct account/environment, verified product permissions, account readiness, Portfolio authorization, envelope/profile version and capital caps. `RequestUpdateBrokerOrder` checks known broker acknowledgement/revision, same account/contracts/legs/quantity/purpose and price limit within the narrower approved and pilot bounds. `RequestCancelBrokerOrder` addresses one known individual order and may remain permitted when new-risk is held. `RecordBrokerExecutionObservation` applies every correlated `execId` fill, including a late fill after cancel, and does not assume TWS `Filled` status alone proves leg balance. `RecordBrokerOrderFailure` distinguishes definitive zero-exposure rejection from ambiguous socket/callback failure; only complete reconciliation can release an unknown attempt.

These guards remain small, explicit and ordered in their **dedicated** Command extensions. An exact OperationId/observation/execId with the same durable content hash is an acknowledged no-op before event construction; the same identifier with different content is a classified conflict. `BrokerOrderCommandState.Apply` returns `true` only for a valid actual transition and leaves state untouched on `false`; `state.Update`/`UpdatedOk` success requires a `true` result. A post-preflight false is an invariant failure, not a successful receipt. The same rules apply to BrokerAccount material snapshot/gate/approval changes and touched OrderExecution states. Provider changes must not introduce transient-only dedupe, unconditional `Update`, full-stream replay per quote or a poll-based recovery loop.

## 4. IBKR connection and callback-routing gate

Pin a tested official C# API version and capture its callback/signature fixtures before implementing. `IbkrSession` owns one physical TWS/IB Gateway connection, one `EWrapper` callback entry, the official reader topology, and a serial outbound dispatcher; OrderExecution and BrokerAccount modules register callbacks with the router before the connection is marked ready. One session epoch increments on reconnect. `nextValidId` and a durable high-water mark seed the order-ID allocator; request/ticker IDs and order IDs live in separate allocator namespaces. The exact configured account is verified on connect and on account observations; foreign account callbacks are quarantined, not assigned to the active account by symbol or order similarity.

IBKR reader callbacks perform bounded normalization/enqueue only. They never run SQL, NATS, Portfolio risk, actor state machines, UI or a micro-execution policy. A critical order/status/execution/commission/error/account/position/completion callback must be retained losslessly or the session/gate becomes degraded with an explicit gap incident. Callback routing preserves account, client/order ID, `permId`, `orderRef`, `execId`, source epoch, callback UTC and receive sequence. Old-epoch facts cannot complete a current account snapshot or authorize a mutation. The serialized outbound dispatcher validates rate/pacing and operation correlation before TWS calls, reports `RejectedLocally`/`AcceptedForDispatch`/`OutcomeUnknown`, and never treats socket write as broker acknowledgement.

Tests use a fake callback adapter and pinned API signature fixtures first. Include connect/refuse/reconnect, stale epoch, wrong account, duplicate/missing `nextValidId`, order-ID high-water recovery, concurrent order/account callbacks, callback overflow, fragmented account downloads, and reader-thread isolation. A disconnected/unknown provider may offer read-only last-known evidence with age/quality markers, but `PlaceNewRisk` stays false.

## 5. Exact contract reference and order materialization gate

Resolve each approved string `ContractId` through exact product-specific contract reference fields and versioned fingerprints: futures root, expiry/value date, exchange, currency, trading class/local symbol where needed; futures option expiry, strike, put/call, multiplier, exchange and underlying. The adapter translates only inside Framework to IBKR `conId` and rejects missing/ambiguous/stale/conflicting matches with a classified ContractResolution failure and the source ContractId. Market-rule tick increments, supported exchanges/routing, BAG leg action/ratio and combo price convention are captured and tested. A provider result must not silently flip side/cash-flow sign or approximate an unsupported four-leg BAG with four unrelated live orders.

Materialize only order shapes accepted by the emulator contract gate and separately qualified for IBKR: one-leg futures limit; two-leg vertical spread BAG limit; four-leg iron-condor BAG limit; Opening and Closing purpose. Verify single-account permissions for **each** actual asset/order shape on Paper and Live; a positive cash balance is not proof of eligibility. IBKR's [account configuration guide](https://www.interactivebrokers.com/en/accounts/configuring-your-account.php) distinguishes product eligibility by actual account subtype/jurisdiction. The user-provided active account must be confirmed to have needed futures/futures-option permissions before test or pilot Place is authorized. Actual margin/collateral values are typed account evidence; the business design calls the account cash-backed without assuming a formal `Cash` subtype.

Application/Framework mapper tests compare every leg ID, signed quantity, exact ContractId, approval hash, overall limit, tick-aligned price, routing/TIF, account alias/environment and close TargetPositionId. Unsupported custom component, mixed strategy, unknown position type, absent contract or market rule fails locally **before** broker mutation. Paper/live profiles are separately allowlisted; a Paper order cannot be dispatched to the Live account even if its numeric IBKR order ID looks valid.

## 6. Order mutations, correlation, callbacks and reconciliation gate

For each committed `BrokerOrderPlaceRequestedEvent`, the unchanged BrokerOrder Event handler calls Application `ITradeBroker.SubmitOrder`; the live Application adapter maps to `IFrameworkOrderExecutionBroker.Submit`. Before `placeOrder`, provider correlation durably reserves `(broker instance, environment, account alias, client ID, order ID, BrokerOrderId, OperationId, payload hash, orderRef)` in PostgreSQL. Use the proven shared-transaction enlistment or post-commit durable ordering from Plan 1; an external TWS socket is **never** inside SQL transaction. An exact replay returns its original local receipt. If the socket outcome may be unknown, never blindly resend: mark `OutcomeUnknown`, block new mutation on that order, and perform bounded order/execution/position reconciliation.

`ModifyOrderLimit` is allowed only for a known working IBKR order/revision, exact unchanged legs/contract/account/quantity/purpose and a newly approved tick-aligned overall price within the frozen envelope/pilot caps. It gets a **new OperationId**; the provider rejects a second in-flight modification or a stale expected revision. `CancelOrder` targets one known correlated IBKR order, gets its own OperationId and produces `PendingCancel`, not terminal `Cancelled`. Global cancel is absent from `ITradeBroker`. Socket write success and `orderStatus` text are corroborating, not definitive fill/cancel proof.

Normalize `openOrder` echo/`orderStatus`, exact individual `execDetails`, `commissionReport`, IBKR errors and connection incidents to the shared application observation union. Correlate by account, orderRef, client/order ID, `permId` and exact `execId`; never infer ownership from price/symbol similarity. Independent execution facts allocate to approved component/leg identities with signed quantity, exact ContractId, price, time, source epoch and currency. Commission may arrive before/after exec or be corrected, and remains a separate cost fact. Delayed/duplicate/out-of-order status and fill callbacks are expected. A correlated late fill after cancel must update exposure and trigger reconciliation; foreign or conflicting facts are quarantined and visible without manufactured exceptions.

Order reconciliation is explicit after startup/reconnect, ambiguous mutation, callback gap, late fill or operator request. Query bounded broker open/completed orders, executions, fees and account positions for exact account/orderRef/attempt/date/epoch; return `Complete`, `Incomplete`, `Conflicting`, or `Unknown` evidence, never assume an empty partial query proves zero exposure. BrokerOrder/OrderExecution actors determine whether to wait, individually cancel, accept fills, compensate under an approved envelope or escalate. The provider cannot autonomously place a new strategic order, close every position or mark a Fund trade settled. Reconciliation has no 2-second database worker or unbounded replay loop.

## 7. Broker account and qualification gate

`IbkrBrokerAccount` uses the same shared connection/epoch but a separate `IFrameworkBrokerAccount` port. On every connect/reconnect it verifies the single allowlisted actual account, subscribes to account summary/download/positions, captures typed cash, settled cash, net liquidation, available funds, buying power, initial/maintenance margin, excess liquidity, currency ledgers and P&L telemetry, and waits for required **completion markers** before publishing a coherent immutable snapshot. No position callback before `positionEnd` is `Unknown`, not zero. Missing/invalid/not-applicable critical values remain distinct, and no implicit multi-currency sum is used. Broker positions/fees/cash are external truth; Portfolio/Fund ledger is internal book. Exact contract/quantity/account reconciliation classifies broker-only, internal-only, mismatched quantity, wrong contract or incomplete evidence.

The shared BrokerAccount actors from Plan 1 receive material account/gate/connection/discrepancy events through the one observation bridge and publish gate snapshots. Their accepted qualification/hold Commands and Query APIs remain the only domain gate authority; provider connection alone cannot mark a Paper or Live scope Accepted. Read-only account/health/reconcile may work before trading promotion. Current account subtype, futures/futures-option permissions, collateral/margin, supported order shapes, actual account ID allowlist and currency completeness are qualification evidence. A critical gap, stale epoch, wrong account or internal/broker discrepancy closes new-risk. Known-order cancel and an explicitly authorized risk-reducing close may remain enabled only when exact broker identity/exposure and transport capability permit them.

### 7.1 Paper qualification and acceptance

After accepted Emulator L0, a reviewer may issue a short-lived **`PaperQualification`** authorization with exact paper account alias, test Fund/source identity, allowed instruments/order shapes, quantity/cost caps and expiry. Paper qualification orders still pass Portfolio acceptance and the standard TradeOrder → OrderExecution → BrokerOrder actor path. Ordinary strategy/manual Paper orders cannot borrow this scope. Test connection, account/permissions, futures and option BAG materialization, acknowledgement, actual paper executions/fees, partial/late fill, modify/cancel, process restart, account snapshots, Portfolio Fund postings, discrepancy/unknown recovery and source-generated error details. Store a version-bound paper evidence manifest; a human reviewer must separately accept it before `PaperTrading` general new-risk is enabled. A paper test result or working socket cannot self-approve.

### 7.2 Limited-capital Live pilot and later review

Only after applicable accepted Emulator **and Paper** manifests, exact Live account permissions/read-only account reconciliation and a separate authenticated approval may `LivePilot` become active. The approval freezes limited **nonzero** total capital-at-risk/reserved-cash-collateral, per-order loss/notional/quantity, supported ContractId roots/strategies/order shapes, allowed Fund(s), concurrent positions, daily stop threshold and validity window. Values are supplied and reviewed at the pilot approval gate; code/config cannot invent or raise them. Portfolio checks before accepting a live order; BrokerOrder checks immediately before Place/Update; the live Application adapter validates account/environment/scope again. The narrowest Portfolio/order/pilot limit applies across multiple Funds and working orders, including partial fills and restarts. `LiveApproved` broader use is a **separate** approval after review of actual pilot fills, closes/cancels, Fund accounting and account reconciliation. The pilot cannot auto-promote on a test pass or elapsed time. No Live order may be sent from a qualification test host running alongside the user's IFM app.

These approvals are human-facing external actions; the implementation work can prepare concrete evidence and review screens first. The final Paper/Live permission to transmit orders is granted only by the applicable approved account scope and actual account readiness. Revoked/expired/version-mismatched approval blocks Place/Update new risk while preserving exact known-order cancel/reconcile capability. Neither Paper nor Live automatically falls back to Emulator.

## 8. Application composition, security, UI and generated logs

`InteractiveBrokersTradeBroker` is the second concrete Application `ITradeBroker` implementation. It accepts the live Framework order and account ports only if broker instance, current epoch, environment and single account match. It maps all Framework DTO fields to existing application contracts, merges streams through the **one** hosted bridge, and offers cheap immutable latest account reads. The API host selects exactly one environment by validated options. Paper and Live require separate account allowlists, client IDs, ports and credentials; environment selection cannot be inferred from a TWS connection success. Startup is: validate options/approval/build/profile/account, register both callback features, connect, seed order IDs, download complete account/position data, reconcile open attempts, publish gate/capability, then permit only the approved scope's new-risk path. Wrong actual account is a startup/dispatch fault.

Actor/API/UI operations expose redacted active cash-backed account, Paper qualification or Live pilot scope, current manifest/approval hashes and caps, session epoch and account completeness, open/foreign orders, executions/fees, source OrderExecution/Fund transaction IDs, discrepancies and exact gate-disabled reasons. Manual UI submissions intended for IBKR still call Portfolio first and use `ExecutionChannel.Broker`; human-entered manual fill evidence, if retained, is a distinct route and never impersonates `execDetails`. No unrestricted IBKR account ID, password, connection string, raw rejection callback or Flex token enters actor messages, routine logs or UI.

Create logging-only `internal static partial` classes `IbkrConnectionLogging`, `IbkrOrderLogging`, `IbkrAccountLogging` and `InteractiveBrokersTradeBrokerLogging` under `Logging`. Only their `[LoggerMessage]` declarations are partial; connection/provider/application/actor classes remain normal non-partial classes. Each declaration uses an audited unique EventId, explicit `LogLevel`, constant named template, typed scalar IDs and `Exception` where needed. Log mode/account alias/epoch, operation/attempt, exact safe ContractId/error category, local receipt, authoritative ack/fill/fee, unknown mutation, callback gap, account snapshot/gate, reconciliation and permission/approval failure. Do not log credentials, full account numbers, raw callback objects, per-tick normal successes or redundant duplicate/no-op paths. Event/Realtime extension handlers log real failures at their boundary, and Command unexpected failures flow through typed actor exception handling with structured source-generated Error records. XML documentation covers all new/modified public methods and private actor handler helpers.

### 9.1 Required behavior tests

Happy cases: exact Paper qualification opening one-leg futures, two-leg vertical and four-leg iron-condor BAG; accepted Paper general order; actual individual `execId` fills and commission leading to the same Trade/Position/Fund accounting path as Emulator; approved Closing order from exit workflow; complete account snapshot and zero-position set after completion; known-order cancel with no fill; LivePilot one allowlisted, capped order with current approval. Edge cases: no accepted Emulator/Paper approval, wrong actual account or environment, missing product permission/collateral, unapproved contract/tick/price convention, duplicate OperationId or conflicting payload, unknown socket outcome, ACK timeout, stale echo/revision, callback gap/overflow, foreign order/execution, duplicate/conflicting exec ID, fee before fill or correction, partial/unbalanced combo legs, cancel/late-fill race, positionEnd absent, broker-only/internal-only discrepancy, approval expiry/revocation/version change, pilot cap across Funds/working orders/partial fills/restart, and wrong Paper order aimed at Live. All failures include stage, account alias, OperationId, ContractId where useful, epoch and safe error classification without normal no-op exceptions.

Run `scripts/Test-CommandActorConventions.ps1`, `Test-EventActorConventions.ps1`, `Test-QueryActorConventions.ps1`, `Test-RealtimeActorConventions.ps1` on touched actor trees; assert parse/validation/receive or parse/receive/exception parity and one handler class per message. Unit tests cover provider mappers/correlation, callback router, account assembly and exact state guards. Integration tests use a fake IBKR callback/session fixture against NATS/PostgreSQL/PortfolioDb and reuse the Emulator framework-port contract suite. Verification tests cover MessagePack compatibility, state `Apply(false)`/pending-event behavior, snapshot complete markers, crash at intent/correlation/socket/callback/actor/accounting boundaries and account/environment isolation. Paper tests are separately labelled and run only under test authorization; Live pilot tests only under explicit LivePilot scope. Any test host must exit before a user live IFM run.

### 9.2 Performance and soak

BenchmarkDotNet compares **Emulator baseline versus live-adapter fixture** for DTO mapping, exact contract lookup, callback normalization/bridge routing, immutable account snapshot reads, hot quote decision path, and operation correlation; report build/API version, payload, account/epoch, allocations/op and latency. A fake-callback soak exercises reader, dispatcher, account snapshot assembler and durable actor handoff under controlled burst/reconnect/late-fill patterns, captures GC/LOH/queue/gate trend, and asserts no lost critical observations. Real Paper/pilot order rates are measured as operational evidence, not compared to synthetic throughput as if IBKR fills had the same capacity. Never tune the callback reader by moving SQL or actor business work onto that thread.

## 10. Final operational and review criteria

The Live adapter implementation is code-complete when shared actor conventions and port suites pass, IBKR callback/correlation/recovery fixtures pass, the provider exposes typed account/readiness and OrderExecution/Fund evidence accurately, normal API/UI builds pass, and the protected mode/gate remains closed without acceptance. Paper is **operationally enabled** only with an applicable accepted Emulator manifest, qualified/accepted Paper manifest, exact account permissions and current readiness. Live pilot is **operationally enabled** only with those acceptances plus its own bounded approval and current Live account readiness. Broader Live requires its own review after real pilot results. Every state and limitation is visible in the account/Actor Health UI; no adapter success, elapsed time or automated agent substitutes for an approval.
