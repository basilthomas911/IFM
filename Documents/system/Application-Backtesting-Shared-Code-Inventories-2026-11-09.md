# Backtesting shared-code feasibility and inventories

Date: 2026-11-09. Status: source review for agreement; **no implementation plan and no application code changes**.

## Finding

Backtesting is feasible using the existing market-data contract, trading actors and broker emulator, with a separate file-fed provider and isolated process/storage configuration. It is **not configuration-only**. Stable message origins and time-dependent business code require a broad shared refactor. Source inspection does not establish that replay is safe or deterministic; those are acceptance criteria for later execution.

A useful positive finding is that the Rust business clock is already explicit and can be controlled. `src/runtime/clock.rs` accepts an application UTC anchor and controlled updates; managed `Delivery/NativeMarketDataRuntime.Live.cs` exposes `ConfigureLive` and `UpdateLiveClock`. These seams can be reused. Existing Rust transport/recovery timers must remain monotonic. A wholesale replacement of Rust clocks or financial actors is not justified.

## Market-data API inventory and required behavior

The CSV gives every exact current signature, file/line, whether it has an interface default, and its required replay behavior. No API member is silently omitted.

Current PostgreSQL rows alone are insufficient for an earlier date unless the configuration baseline explicitly establishes their validity then. |

| Five-minute and general indicator seeds | Manifest-backed history before the current replay instant, sufficient warm-up per indicator/timeframe, normal snapshot/history request semantics and shared replay reuse. |

Current implementations/adapters are `DataBento/DatabentoMarketDataApi.cs`, `Remote/MarketDataApiClient*.cs`, `Remote/MarketDataReadMirror*.cs`, and Rust `managed/Api/RustMarketDataApi*.cs`. The remote client forwards asynchronous methods through `Remote/MarketDataApiCall.cs`; synchronous observations use the mirror. Rust facade prototype and dataset-owner constructors are distinct: prototype availability is not evidence that a production replay source exists. The new emulator should implement `IMarketDataApi` and populate the existing contracts/mirror; it should not copy the live provider or relax unsupported defaults.

`NativeBackendServices.AddNativeMarketDataBackend` currently rejects a non-`DatabentoLive` source. Preserve that guard. Introduce a separate Backtesting composition root. Rust `src/historical/file.rs` supplies bounded DBN decoding, not a complete historical-live emulator: subscription selection, point-in-time availability, publication, seeds, session boundaries and causal completion remain needed.

## Clock ownership

| Time domain | Must control | Must not control |
| --- | --- | --- |
| Run market clock (`TimeProvider`) | Trading/session dates, bar closes, signal and strategy business time, quote freshness, pricing expiry, broker-emulator latency and trading timers, five-minute simulated indicator-health checks | Socket timeouts, process shutdown, database command timeouts or operator cancellation |
| Physical clock / monotonic elapsed time | Startup/stop bounds, NATS/DB I/O, worker liveness, missing-output diagnostics, claim/retry leases, progress-stall watchdog, benchmarks and UI responsiveness | Market valuation or historical source dates |
| Source clock | Original exchange event/receive timestamps and publication availability | Must not be overwritten with either replay dispatch time or today's clock |

An event needs several distinct times: exchange event time, historical availability/receive time when supplied, application origin captured at creation, and physical receipt/processing diagnostics. Do not conflate them. Replay ordering must use the documented source/availability sequence, not every message's origin or a UUID timestamp. Warm-up is restricted to data available before the run boundary; it must not place trades before Start.

The C# inventory includes 941 direct wall-clock candidates, 502 injected-clock reads, 124 system composition/fallback sites, 530 physical/mixed timer sites, 33 scheduling/mixed timer sites, 401 monotonic measurement sites, 306 legacy-path sites, 62 UUID-generation sites, 22 business-date calls, six conversions and six diagnostic-classified sites. These are review categories, **not 2,933 required replacements**. Some clock reads in infrastructure are correctly physical. Methods containing both kinds need separate dependencies, not a file-wide clock replacement.

## Exact shared changes needed

The following is a change-boundary specification, not an execution sequence or implementation plan. Names for new metadata types are proposed. The target shared contract is `MessageOrigin(OriginatedAtUtc, ClockDomainId, RunId, CausationId)` with UTC represented as an explicit `DateTimeOffset`; optional causation/run values are absent for ordinary live messages. A versioned origin header set must use an unambiguous UTC representation (round-trip ISO 8601 or a documented integer epoch unit), with the same encoding in Rust and .NET. Never serialize unspecified/local DateTime as origin. Existing paths and method examples are verified; the CSVs identify the wider per-call/per-contract scope.

## Origin and wire compatibility contract

1. The message-creation boundary captures origin from its injected market clock once. For direct actor invocations and post-commit effects, the same creation service supplies metadata before persistence. Publishing is not allowed to invent a fresh origin on each retry.
2. A new command/query/event/reply has a new origin; copied/retried messages preserve theirs. Keep the triggering message's identity/time as causation rather than falsely giving every downstream event its parent's origin.
3. Transport origin travels as additive metadata. Persist it independently with events/command audit/outboxes so headers are not the only copy. A run/domain identity prevents cross-environment contamination; namespace/credentials additionally enforce isolation.
4. Keep exchange event/receive times intact. Source records released late may have earlier event time; this alone must not suppress an ITI workflow. Ordinary deduplication/idempotency remains.
5. Old serialized events still decode using existing keys. Old messages without origin are explicitly marked legacy/unknown or inferred from a documented stored field with provenance. Historical unknown origin cannot become today's UTC. New Backtesting messages require complete metadata.
6. Request hashes and event/effect IDs must retain their existing documented business meaning. The origin addition must not create duplicate commands on retries or alter existing `CompositionSemanticHash` exclusions.

This is the recommended common mechanism. It avoids adding one inherited payload property at the same numeric key to every command/event, while still correcting real business consumers of `OriginatedOn`. It does require shared transport/context and durable storage changes; an emulator adapter alone cannot solve it.

## Protecting live trading: required evidence before rollout

| Risk | Evidence required |
| --- | --- |
| Simulated clock reaches Development/live | Startup guard for environment, PostgreSQL database identity, Scylla keyspace, NATS namespace and broker/provider capabilities; restricted credentials; test that System remains the live default. Every accepted Start resets all run mutable stores only after old workers/producers/outboxes are fenced. |
| Incorrect dates, freshness or expiries | Frozen/advancing clock unit tests across midnight, futures 18:00 boundary, DST, weekends and expiry; live-mode equivalence tests; preserve valid NoTrade and no weak freshness bypass. |
| Wire/persisted-event breakage | Golden old/new MessagePack/JSON fixtures, NATS commands/queries/events/replies, pooled/fanout paths, outbox crash/retry/restart and latest-snapshot-plus-tail PostgreSQL tests. Stable origins and IDs must survive all paths. |
| Replay deadlock, dropped bars or look-ahead | Pause/stop/stall tests, bounded real watchdog, causal completion through bars/indicators/ITI/workflows/outboxes/broker/settlement; source availability ordering and deterministic tie-breaks. Queue depth or native readiness alone is insufficient. |
| Financial/order regression | Existing rejection, timeout, pending, partial fill, Change Limit, Cancel, late-fill and reconciliation tests; positions/Fund settlement and no duplicates across restart. No core financial rule changes justified by replay. |

## Boundary before the implementation plan

These three inventories are complete for the declared source/search scope. They identify the required shared seams and exact candidate locations; they are not a certification of transitive reachability or runtime safety. Remaining proof questions are whether the chosen real historical manifest contains all required point-in-time inputs, whether a causal completion barrier can cover the existing asynchronous paths without broad actor rewrites, and whether per-site clock classification preserves live behavior. No blocker requiring a trading-rule rewrite was established by this source review.

Recommendation: agree on the two-clock model, common durable message-origin metadata, explicit Replay backend ownership, and separate Backtesting composition before creating the implementation plan. The eventual proof must exercise one real historical slice through indicators/ITI/workflow and a broker lifecycle through settlement, then a second fresh Start with no state leakage. If that requires weakened risk/data rules or broad live recovery rewrites, revise the design first.

The UI remains exactly as requested: **Backtesting menu after System; selecting it adds/focuses one existing-style tab in the center pane. All other panes and tabs stay in place.**
