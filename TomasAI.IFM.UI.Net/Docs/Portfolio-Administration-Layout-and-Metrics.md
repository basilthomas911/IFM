# Portfolio Administration layout and Fund metrics

Underlyings, Asset Types, Directions and Market Conditions use the shared [checked dropdown](Checked-Dropdown-Control.md), with a read-only comma-separated selection summary. The list sources are the published Databento product index and the grouped [ConfigurationDb lookup definitions](../../TomasAI.IFM.Application.Storage/Docs/ConfigurationDb-Lookup-Definitions.md). CSV entry is no longer required or permitted in these four controls.

The main area has three equal-width columns: **Portfolios**, **Funds**, and **Selected Fund Details**. The first list selects a Portfolio, the second lists its Fund mandates, and the third shows Fund information plus Allocation, Risk Envelope and Trade Assignments tabs. Each section has its own wrapping action toolbar. The columns resize together; grids retain scrolling for longer records.

**Create Fund...** opens the editor even when the ConfigurationDb deployment list is empty. A new Fund starts in Draft and may be saved without strategy permissions while deployments are being configured. **Change Fund...** edits the selected Fund and saves the next immutable mandate version under the same Fund ID. The editor and selected-fund summary display the allocated Fund ID, with no separate Fund Code field. The required compatibility `FundCode` is generated internally as `FUND-{FundId}` for new funds and preserved exactly for existing funds. Single-line labels and controls share a vertical center; the permission-list label aligns with the top of the list. Existing unavailable permissions remain visible and must be explicitly unchecked before removal. A failed save stays visible in the operation status instead of being overwritten by an automatic refresh. Catalog request failures still display an error rather than being interpreted as an empty catalog.

The three default strategy families are grouping definitions, not executable deployments. An unassigned schema-v3 Draft has both permission arrays empty and grants no trading authority. It can also be disabled or retired. Activation still requires exact configured permissions and the existing Portfolio/assignment/profile checks. Rebuild both API and UI for this validation and editor change; no database schema migration is needed.

Fund editing verification covers actual Create Fund/Change Fund button clicks and modal Save with an empty deployment catalog, both successful and rejected command replies, unchanged Fund identity and incremented mandate version, and persistent failure status. Domain checks cover unassigned creation/versioning/replay, forbidden activation, permission removal without legacy fallback, older-schema validation, and disabled/retired history. These UI tests use mocked services and do not populate the application databases.

The final two rows span the window: ten metric headings, then ten read-only values. Metrics are Win Rate, Average Profit, Loss Rate, Average Loss, W/L Ratio, Sharpe Ratio, P&L amount, P&L percentage, Commission, and Maximum Drawdown percentage. Amounts use the selected Fund risk-envelope currency, falling back to its Portfolio base currency. All controls use the Dark Trading Theme and Microsoft Sans Serif 10pt.

The visible From/To dates initially cover the current calendar year through today. Both endpoints are inclusive in the UI and in the underlying Fund timeline query; the API receives the exact selected dates. Date changes and Refresh Metrics load the selected Fund report independently of configuration. Selecting another Portfolio/Fund clears old metrics immediately and cancels observation of the previous request. A late response cannot replace the current selection. Missing history, unavailable reports and invalid date ranges show N/A with an explanation. This adds no write operation or schema migration to Fund storage.

## Calculation and compatibility

The existing Fund report provides the nine legacy metrics; their calculations are retained. In particular, the legacy W/L value is the weighted win-profit/loss ratio, and Sharpe is the existing annualized daily-balance-return estimator. These are recorded Fund accounting metrics, not a newly introduced cash-flow-adjusted investment-performance model.

Maximum Drawdown uses every ledger transaction's recorded balance, ordered by value date, transaction timestamp and transaction ID, seeded with the balance immediately before the first transaction in the period. The amount is the largest decline from a preceding running peak. The percentage is the largest proportional decline from a positive peak; it need not occur at the same point as the maximum amount. The amount is available in the percentage field's tooltip. No transaction history yields no drawdown; a history without a positive peak yields no percentage.

This is **recorded balance drawdown**, including deposits/withdrawals and any recorded P&L. It excludes unrealized P&L that has not been posted. The UI tooltip identifies this basis. Daily balance snapshots are unsuitable for this calculation because the existing query retains each day's maximum, potentially hiding a later trough.

The existing `FundPnlReportReadModel` MessagePack keys 0–9 remain unchanged. Optional keys 10–12 add maximum drawdown amount, maximum drawdown percentage and history availability. Older producers leave availability unknown, so the new metrics strip displays N/A rather than fabricated zero values. Rebuild/restart both the API and desktop to use the extended report.

Verification covers chronological peak-to-trough declines, recovery, empty history, non-positive capital, same-day troughs, report serialization, stale asynchronous responses, invalid dates, reporting failure, equal columns and metric/control bounds at default and minimum window sizes.

Builds used an isolated output directory because the running API held its normal binaries open; no live API restart or database mutation was performed.
